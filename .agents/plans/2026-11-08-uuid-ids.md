# Standardize every database id on UUID

**Status:** Implemented — awaiting review

Related: `2026-11-05-multi-account-auth.md`, `2026-11-08-dev-auth-impersonation.md`

## Problem

The database currently mixes several kinds of ids:

- Domain rows (`projects`, `invoices`, `hour_entries`, `furniture_items`,
  `invoice_line_items`) use `text` columns filled with `crypto.randomUUID()`.
- Better Auth rows (`user`, `session`, `account`, `verification`) use `text`
  columns filled with Better Auth's 32-character random strings.
- Development fixtures use arbitrary ids such as `test-client-0001`, and the
  auth migration uses a synthetic `legacy-owner` id.

Because every id is `text`, Postgres cannot enforce UUID shape and the schema
does not communicate the intended format. The auth feature is not merged yet,
so this is the cheapest point to fix it.

## Desired outcome

Every primary key and every foreign-key/identifier column that points at a row
is a Postgres `uuid`:

- `user.id`, `session.id`, `account.id`, `verification.id`
- `session.user_id`, `session.impersonated_by`, `account.user_id`
- `projects.id`, `projects.owner_id`
- `invoices.id`, `invoices.owner_id`, `invoices.project_id`
- `invoice_line_items.id`, `invoice_line_items.invoice_id`,
  `invoice_line_items.source_id`
- `hour_entries.id`, `hour_entries.project_id`, `hour_entries.invoice_id`
- `furniture_items.id`, `furniture_items.project_id`,
  `furniture_items.invoice_id`

Non-row identifiers stay `text`: provider account ids, session tokens, invoice
numbers, dates, and arbitrary labels.

## Approach

1. **Change the Drizzle schema.**
   - Import `uuid` from `drizzle-orm/pg-core`.
   - Every primary key becomes `uuid('id').primaryKey().defaultRandom()`.
   - Every column listed above becomes `uuid(...)`; nullable columns stay
     nullable.
   - Keep all existing indexes, uniqueness constraints, and foreign keys.
     `invoices.project_id` currently has no foreign key, so it stays a UUID
     without one to keep this change scoped to id types.
   - `invoice_line_items.source_id` is polymorphic (hours or furniture), so it
     becomes `uuid` without a foreign key.

2. **Tell Better Auth to generate UUIDs.**
   - Set `advanced.database.generateId: 'uuid'` in `lib/auth.ts`. Better Auth
     then uses `crypto.randomUUID()` for users, sessions, accounts, and
     verification rows.
   - Existing domain writes already pass `crypto.randomUUID()`, which satisfies
     the UUID columns. The DB defaults are a second safety net.

3. **Replace the migration history with one clean baseline.**
   - Delete `lib/db/migrations/0000`–`0003` and the `meta/` snapshots/journal.
   - Run `pnpm db:generate` to produce a single initial migration from the
     updated schema.
   - This removes the hand-written `legacy-owner` insert and the
     text-to-owner-column migration. There is no data to preserve.

4. **Reset local development data.**
   - Drop and recreate the `public` and `drizzle` schemas in the local
     `maison_dev` database.
   - Run `pnpm db:migrate`.
   - Recreate the local test account with a real UUID if it is needed for
     impersonation testing, and update `IMPERSONATE_USER` to that UUID.

5. **Update docs.**
   - Remove the `legacy-owner` note from `AGENTS.md`; a fresh database has no
     legacy rows.
   - Note that `IMPERSONATE_USER` must be a UUID.
   - Update the PR description and deploy steps to replace the backfill steps
     with "reset the database once, then sign in".

## Alternative considered

**Keep the existing migration history and add a destructive `0004` migration
that truncates rows and casts `text` to `uuid`.**

Rejected because the user explicitly allowed deleting all rows and said no
data-preserving migration is needed. A clean baseline is simpler, removes the
`legacy-owner` placeholder entirely, and avoids carrying arbitrary test ids
through casts. The cost is that production must be reset once rather than
upgraded in place; that will only happen after explicit approval.

## Files and modules affected

- `lib/db/schema.ts`
- `lib/db/auth-schema.ts`
- `lib/auth.ts`
- `lib/db/migrations/` (delete and regenerate)
- `AGENTS.md`
- `.agents/plans/2026-11-08-uuid-ids.md`

`lib/repository/postgres.ts`, services, API routes, and client components keep
using `string` ids, so they should not need changes.

## Acceptance criteria

- No `text('id')` or `text('<something>_id')` remains in the Drizzle schema.
- `pnpm db:generate` creates one baseline migration whose id columns are
  `uuid` and whose foreign keys reference UUID columns.
- A freshly reset local database migrates cleanly.
- `npx tsc --noEmit` and `pnpm build` pass.
- Creating a project, logging hours, adding furniture, generating an invoice,
  and reading the invoice all work with UUID ids.
- Admin sign-in and impersonation work with UUID user ids.
- `IMPERSONATE_USER` with a UUID resolves the account; a non-UUID value fails
  clearly instead of producing an opaque Postgres cast error.

## Risks and open questions

- **Production data loss.** Resetting production is a separate destructive
  step and needs explicit approval after local verification. No production
  reset or migration will run as part of this implementation.
- **Better Auth must generate UUIDs before the first user is created.** Setting
  `advanced.database.generateId` is part of this change; without it, inserts
  into `uuid` columns fail.
- **Existing sessions and cookies become invalid** after the reset. That is
  expected.
- **The migration baseline replaces history.** Any environment still on the
  old migrations must be reset, not incrementally migrated.
